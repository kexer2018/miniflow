# miniflow 产品化实施方案

> 日期: 2026-07-31
> 目标: 从 CLI 容器执行器演进为可视化流水线平台
> 上层约束: 以 `docs/product-principles.md` 为准

---

## 1. 目标与非目标

### 1.1 目标

miniflow 的实施目标是形成一个完整的可视化流水线产品闭环：

```text
选择基础 Step → 拖拽连线 → 配置参数 → 校验 → 运行 → 看状态/日志 → 保存产物 → 诊断失败
```

后端继续以 Docker 为底层执行器。每个 Step 使用临时容器执行，默认挂载同一个 workspace，使前后 Step 可以通过文件传递产物。

实施时必须遵守五条产品边界：Docker 主路径、单机优先、脚本优先、图形化只提供基础 Step、PipelineSpec 作为稳定协议。

### 1.2 非目标

近期不做：

- 复杂业务模板。
- 自然语言生成整条流水线。
- AI 自动修改并执行修复。
- 分布式 Worker 调度。
- 非 Docker executor。
- 插件市场。
- 多租户权限系统。

这些能力应等 Step Registry、Run API、Artifact/Cache/Secret 模型稳定后再推进。

## 2. 技术栈

| 层 | 选择 | 说明 |
|----|------|------|
| 后端语言 | Go | 与当前代码一致，适合容器编排和单二进制部署 |
| 运行环境 | Docker SDK | 当前已有 `internal/container`，近期唯一主执行后端 |
| 数据库 | SQLite | 当前已有，产品早期足够；后续可抽象 PostgreSQL |
| API | Go `net/http` | 当前已有骨架，先保持轻量 |
| 前端 | React + DAG/flow 画布库 | 适合 Step Palette、Canvas、Inspector 结构 |
| 日志流 | SSE 优先 | 实现比 WebSocket 简单，足够覆盖单向日志和状态推送 |
| AI | OpenAI-compatible LLM + RAG seed | 继续作为诊断和字段建议能力，不作为主路径 |

Go 版本以 `go.mod` 为准，当前为 Go 1.25。

## 4. 数据模型演进

### 4.1 兼容现有 Step

旧格式继续支持：

```json
{
  "name": "test",
  "image": "golang:1.25",
  "commands": ["go test ./..."],
  "depends_on": ["checkout"]
}
```

兼容策略：

- 如果 `type` 为空且存在 `commands`，视为 `script.run`。
- 旧字段继续映射到 internal pipeline Step。
- CLI 第一阶段不强制用户迁移。

### 4.2 新 typed step

```json
{
  "name": "test",
  "type": "script.run",
  "image": "golang:1.25",
  "depends_on": ["checkout"],
  "with": {
    "workdir": "/workspace",
    "shell": "sh",
    "script": "go test ./... -count=1"
  }
}
```

### 4.3 Step Type Definition

建议后端定义：

```go
type StepTypeDefinition struct {
    ID          string
    Name        string
    Group       string
    Description string
    Icon        string
    Schema      map[string]any
    Defaults    map[string]any
    Compile     StepCompiler
}
```

职责：

- 给前端渲染表单。
- 给 API 做参数校验。
- 给执行器编译 internal step。
- 给 AI/助手提供合法 Step 边界。

## 5. 分阶段实施

### Phase A: 当前可用性修正

目标：把现有 CLI 和文档状态修准，减少后续产品化摩擦。

任务：

1. 修复 `validate -f`。
2. 同步 README、docs、Dockerfile 中的 Go 版本描述。
3. 增加 Docker 不可用时的清晰错误提示。
4. 为 source checkout、timeout、secret 注入补测试。
5. 保留当前 JSON 执行路径。

验收：

- `miniflow validate -f examples/go-ci.json` 可用。
- `go test ./... -count=1` 通过。
- Docker 可用时最小示例可执行。

### Phase B: Step Type Registry

目标：建立基础 Step 平台的后端核心。

任务：

1. 扩展 `pkg/pipeline.StepSpec`，增加 `Type string` 和 `With map[string]any`。
2. 新增 Step Registry 包。
3. 实现 `script.run` definition。
4. 实现 `git.checkout` definition。
5. 编译 typed step 到 internal step 或 source action。
6. 暴露 `GET /api/v1/step-types`。
7. 暴露 `POST /api/v1/pipelines/validate`。

验收：

- API 返回 Step 类型和 schema。
- `script.run` 可以通过 typed spec 执行。
- `git.checkout` 可以作为 typed step 出现在 DAG 中。
- 旧 spec 不破坏。

### Phase C: Run Service

目标：前端可以启动并观察 pipeline 运行。

任务：

1. 定义 Run、StepRun 数据模型。
2. 扩展 SQLite schema。
3. 实现 `POST /api/v1/runs`。
4. 实现 `GET /api/v1/runs/{id}`。
5. 实现 `GET /api/v1/runs/{id}/steps`。
6. 实现 `POST /api/v1/runs/{id}/cancel`。
7. 把 executor 改为可发出状态事件。

验收：

- API 可以异步启动一次运行。
- 查询 run 能看到整体状态。
- 查询 steps 能看到每个节点状态。
- 可以取消运行。

### Phase D: 日志流与诊断视图

目标：让图形化运行具备实时反馈。

任务：

1. 定义 Step 日志事件。
2. 将 container log collector 接到 run event bus。
3. 实现 SSE：`GET /api/v1/runs/{id}/events`。
4. 日志推送前默认走脱敏。
5. Step 失败后触发分类和诊断。
6. 将 diagnosis result 关联到 step run。

验收：

- 前端能实时看到日志。
- 失败节点能看到分类和诊断建议。
- secret 不出现在推送日志中。

### Phase E: Artifact 与 Cache

目标：补齐产品化流水线的输入输出模型。

任务：

1. 定义 artifact metadata。
2. 增加本地 artifact store。
3. 实现 `artifact.save`。
4. 实现 `artifact.restore`。
5. 定义 cache key 模板解析。
6. 实现 `cache.restore` 和 `cache.save`。
7. 记录 cache hit/miss。

验收：

- Step 可以保存 artifact。
- UI/API 可以列出和下载 artifact。
- 下游 Step 可以恢复 artifact。
- cache 命中状态可查。

### Phase F: Secret/Credential API

目标：替代纯本地文件型凭据管理。

任务：

1. 定义 secret metadata。
2. 实现 secret create/update/delete/list。
3. 值加密或至少限制明文回读。
4. 支持 Git credential、registry credential、generic token。
5. Step 运行时解析引用。

验收：

- 前端可以选择 secret。
- pipeline spec 中只保存 secret 引用。
- 日志脱敏覆盖 secret 值。

### Phase G: 前端 MVP

目标：实现可视化编辑和运行闭环。

页面：

1. Pipeline Editor。
2. Run Detail。
3. Run History。
4. Secret Settings。

核心组件：

1. Step Palette。
2. DAG Canvas。
3. Step Inspector。
4. Bottom Panel。
5. Raw Spec Preview。

验收：

- 用户能拖拽创建 Step。
- 用户能连线形成 DAG。
- 用户能配置脚本、镜像、env、secret、cache、artifact。
- 用户能运行并看状态/日志。
- 用户能从失败节点进入诊断视图。

## 6. 前端交互设计重点

### 6.1 Step Palette

分组：

- Source
- Script
- Files
- Cache
- Artifacts
- Docker
- Integration
- Control

每个 Step 卡片显示名称、图标、简短说明。用户拖拽到画布创建节点。

### 6.2 DAG Canvas

节点显示：

- Step 名称。
- Step 类型。
- 状态。
- 耗时。
- 错误标记。

连线只表达依赖关系。复杂数据传递不要用线表达，使用 artifacts/cache/workspace 面板表达。

### 6.3 Step Inspector

Tab：

- Basics
- Configure
- Environment
- Inputs & outputs
- Policy
- Advanced

`Configure` 根据 Step type schema 动态渲染。

### 6.4 控件选择

| 字段 | 控件 |
|------|------|
| Step name | input |
| Type | 创建时选择，后续谨慎修改 |
| Image | combobox |
| Script | code editor |
| Env | key/value table |
| Secret | picker |
| Cache key | key builder |
| Artifact path | path/glob input |
| Timeout/retry | number input + toggle |
| HTTP method | segmented control |
| HTTP body | code editor |

## 8. 风险与应对

| 风险 | 应对 |
|------|------|
| typed step 破坏旧 spec | 保持兼容，旧格式视为 `script.run` |
| 前端表单与后端 schema 不一致 | Step Registry 成为唯一事实来源 |
| artifact 与 workspace 语义混乱 | workspace 负责运行中传递，artifact 负责持久化和下载 |
| Docker build 需要宿主 Docker 权限 | MVP 可先 shell 模板，产品化后由 runner 原生调用 Docker API |
| Secret 泄露 | spec 只存引用，日志推送前脱敏 |
| 过早做 AI 编排 | AI 仅用于诊断和字段建议，整图生成后置 |
| 过早做分布式或非 Docker executor | 单机 Docker 闭环完成后再评估 |

## 9. 推荐下一个开发切片

最小可交付切片：

1. 修复 CLI `validate -f`。
2. 扩展 StepSpec：`type`、`with`。
3. 新建 Step Registry。
4. 实现 `script.run`。
5. 实现 `git.checkout`。
6. 添加 Step Types API。
7. 添加 Validation API。

这个切片完成后，前端就可以开始基于真实 Step schema 做 Step Palette 和 Inspector，而不是写死表单。
