# miniflow — AI 原生轻量级 CI/CD 执行引擎 实施方案

> **本文档定位**：技术方案 + 分阶段实施计划。讨论确认后据此动手编码。
>
> **核心原则**：Phase 1 独立发布，不等 Phase 2。CLI 先行，Web UI 后续。

---

## 一、技术栈锁定

| 层面 | 选型 | 理由 |
|:---|:---|:---|
| **后端语言** | **Go 1.23+** | 容器编排 + 网络分发，goroutine 天然胜任，Docker SDK 成熟，编译快速，招聘友好 |
| **容器 SDK** | `github.com/docker/docker/client` | 官方维护，API 覆盖全面 |
| **CLI 框架** | `github.com/spf13/cobra` | Go 生态 CLI 事实标准 |
| **日志/结构化** | `slog`（标准库）+ `encoding/json` | Go 1.21+ 自带，零依赖 |
| **数据库** | PostgreSQL（底座）+ Redis（缓存） | 白皮书 9.3.6 建议，Phase 1 先用 SQLite 简化 |
| **LLM SDK** | 标准 HTTP + SSE（模型无关抽象层） | 不绑定特定厂商 |

**不做 Rust 双轨并行**（白皮书 9.5 建议）。

## 三、Phase 1 详细方案：报错分析与自动修复提示

### 3.1 核心流程

```
用户执行流水线 (CLI)
    │
    ▼
Worker 逐 Step 拉起临时容器执行
    │
    ▼
某 Step 失败 → 容器 exit 1
    │
    ▼
collector 实时采集 Stdout/Stderr
    │
    ▼
sanitizer 脱敏（正则层）
    │
    ▼
classifier 分流
    ├── 应用代码错误 → 只读输出解析结果
    └── 基础设施错误 → analyzer 分析
                            │
                            ▼
                       LLM + RAG 种子库 → 生成修复建议卡片
                            │
                            ▼
                       输出建议到终端 + 询问是否重试
```

### 3.2 数据模型

```go
// Step 执行结果
type StepResult struct {
    Name       string `json:"name"`
    Status     string `json:"status"` // success / failed
    ExitCode   int    `json:"exit_code"`
    RawLog     string `json:"raw_log"`
    Sanitized  string `json:"sanitized_log"`
    DurationMs int64  `json:"duration_ms"`
}

// 日志分类结果
type Classification struct {
    Type    LogType // app_error | infra_error | unknown
    Reason  string
    Signals []string // 匹配到的信号词
}

type LogType string
const (
    AppError  LogType = "app_error"   // 只读解释
    InfraError LogType = "infra_error" // 触发修复流
    Unknown   LogType = "unknown"
)

// 修复建议
type FixSuggestion struct {
    StepName     string `json:"step_name"`
    RootCause    string `json:"root_cause"`
    FixPlan      string `json:"fix_plan"`
    Confident    float64 `json:"confident"` // 0-1
    SuggestedFix *StepFix `json:"suggested_fix,omitempty"`
}

type StepFix struct {
    Description string `json:"description"`
    // 覆盖的配置字段
    ConfigOverride map[string]any `json:"config_override"`
}
```

### 3.3 Log Classifier 分流规则（确定性的，不需要 LLM）

| 信号词 | 分类 | 示例 |
|:---|:---|:---|
| `panic:`, `SyntaxError`, `NullPointer`, `TypeError`, `undefined is not a function` | `app_error` | 应用代码抛异常 |
| `Traceback (most recent call last)` | `app_error` | Python 异常 |
| `exit code 1` + 无其他信号 | `unknown` | 兜底 |
| `401 Unauthorized`, `403 Forbidden` | `infra_error` | 鉴权失败 |
| `no such image`, `manifest not found` | `infra_error` | 镜像拉取失败 |
| `Connection refused`, `dial tcp`, `TLS handshake timeout` | `infra_error` | 网络连接问题 |
| `Permission denied`, `cannot open file` | `infra_error` | 文件权限问题 |
| `no space left on device` | `infra_error` | 磁盘空间不足 |
| `authentication required`, `certificate has expired` | `infra_error` | 凭证过期 |
| `could not find`, `not found` + 涉及 config/credential 上下文 | `infra_error` | 配置缺失 |

### 3.4 RAG 种子案例结构（Phase 1 手动构建 50-100 条）

```yaml
# seeds/image-pull.yaml
- id: "img-001"
  category: "image_pull"
  title: "镜像不存在于仓库"
  match_pattern:
    - "no such image"
    - "manifest for .* not found"
    - "not found: manifest unknown"
  raw_log_example: |
    docker: Error response from daemon: manifest for golang:1.99 not found: manifest unknown: manifest unknown.
  sanitized_log: |
    docker: Error response from daemon: manifest for <IMAGE> not found.
  root_cause: "指定的容器镜像标签在目标仓库中不存在（可能是拼写错误、标签名变更或仅存在于私有仓库）"
  fix_suggestion:
    description: "修正镜像标签为已存在的版本"
    config_override_example:
      image: "golang:1.22"
```

### 5.1 容器 UID 统一策略

```go
// 所有容器统一以 UID 1000:1000 运行
// 启动前对共享工作空间执行 chown
func (m *Manager) EnsureWorkspacePermissions(workspacePath string) error {
    // docker run --rm -v workspacePath:/workspace --user 1000:1000 \
    //   alpine chown -R 1000:1000 /workspace
    // 约束：基础镜像必须支持 --user 1000 运行
}
```

### 5.2 日志脱敏第一层（正则覆盖 Top 80%）

```go
// 脱敏规则优先级由高到低
var sanitizeRules = []SanitizeRule{
    {Pattern: `Bearer\s+eyJ[a-zA-Z0-9_-]+\.eyJ[a-zA-Z0-9_-]+\.[a-zA-Z0-9_-]+`, Replace: "Bearer ***JWT***"},
    {Pattern: `AKIA[0-9A-Z]{16}`, Replace: "***AWS_KEY***"},   // AWS Access Key
    {Pattern: `(?:https?://)[^:]+:[^@]+@`, Replace: "***CREDENTIALS@"}, // Basic Auth in URL
    {Pattern: `-----BEGIN (?:RSA |EC |OPENSSH )?PRIVATE KEY-----`, Replace: "***PRIVATE_KEY***"},
    {Pattern: `[a-zA-Z0-9_\-]{40,}`, Replace: "***HIGH_ENTROPY***"}, // 高熵字符串兜底
}
```

### 5.3 Pipeline JSON Schema（Phase 1 支持的格式）

```json
{
  "version": "1.0",
  "name": "go-ci",
  "workspace": "/workspace/go-project",
  "steps": [
    {
      "name": "checkout",
      "image": "alpine/git:latest",
      "commands": ["git clone https://github.com/user/repo.git ."],
      "cache": false
    },
    {
      "name": "test",
      "image": "golang:1.22",
      "commands": ["go test ./..."],
      "depends_on": ["checkout"],
      "cache": {
        "path": "/go/pkg/mod",
        "key": "go-mod-{{ checksum \"go.sum\" }}"
      }
    }
  ]
}
```

### 5.4 错误处理原则

- **底层错误全部包装**：使用 `fmt.Errorf("context: %w", err)` 携带上下文
- **容器执行失败**：不 panic，返回清晰的 `StepResult`（含 ExitCode + 原始日志）
- **LLM 调用失败**：降级输出基础分析（"无法连接 AI 服务，以下为原始日志…"），不阻塞流程
- **脱敏失败**：保守策略——宁可漏脱敏不可误脱敏（白皮书 9.3.3 建议）

### ✅ 已确认

| # | 问题 | 决策 | 备注 |
|:---|:---|:---|:---|
| 1 | DAG 输入格式 | **JSON** | LLM 直接输出 JSON，前后端天然对齐，Go 标准库原生支持。后期可按需加 YAML 转换层 |

## 八、AI 功能场景分析与分阶段实施建议（基于代码库现状）

> 本章基于 `miniflow` 代码库的完整源码审查，分析三个 AI 功能场景的技术可行性、工程成本、依赖前置条件和实施顺序。

### 8.1 场景一：执行记录报错诊断（Passive Diagnostic）

| 维度 | 评估 |
|:---|:---|
| **状态** | 🟢 **低成本，高即时回报。当前最合理的起点。** |
| **核心技术** | 失败日志 → Sanitizer 脱敏 → Classifier 分流(确定性) → LLM 诊断 + RAG 知识库检索 |

#### 代码基础设施评估（已完成部分）

| 组件 | 文件 | 状态 | 说明 |
|:---|:---|:---:|:---|
| Log Collector 实时采集 | `internal/log/collector.go` | ✅ **已完成** | bufio.Scanner + 64KB buffer/1MB max line + goroutine 回调 |
| Log Sanitizer 脱敏 | `internal/log/sanitizer.go` | ✅ **已完成** | 8 条正则规则，保守策略，覆盖 JWT/AWS/SSH/GitHub/npm/Docker/高熵 |
| Log Classifier 分流 | `internal/log/classifier.go` | ✅ **已完成** | 确定性信号词匹配（无 LLM），`app_error` / `infra_error` 二分 |

#### 新增代码工作量估算

| 任务 | 估算 | 依赖 |
|:---|:---:|:---|
| 补全 `internal/llm/`：定义 `LLMClient` 接口、流式/非流式调用 | 2 天 | 无 |
| 补全 `internal/fixer/`：RAG 引擎（加载 seeds/YAML）、诊断 prompt 构建 | 3 天 | LLM 接口完成 |
| `seeds/` 扩充：从当前 9 条 → 50-100 条覆盖 Top 80% 故障 | 3-5 天 | 需要运维经验积累 |
| 新增诊断 API：`POST /api/v1/diagnose/failure` | 0.5 天 | fixer 引擎完成 |
| 前端：失败步骤旁 [✨ AI 智能诊断] 按钮 + 结果面板 | 1-2 天 | API 完成 |

#### 需改进的细节

1. **种子库存储架构演进**：当前 `seeds/` 是静态 YAML 硬编码。建议分两层：
   - **静态层**（`seeds/*.yaml`）：编译时嵌入，作为 LLM prompt 的 few-shot 示例
   - **动态层**（SQLite `seed_cases` 表）：运行时积累的历史故障案例，作为动态上下文注入

2. **修复建议链接支持**：种子数据结构需要扩展 `doc_url` 或 `fix_ref` 字段，使前端可以跳转内部文档。当前仅有 `config_override_example`。

3. **脱敏语义化**：当前 `Sanitizer` 将敏感信息替换为 `***JWT***`/`***AWS_KEY***` 等标记，LLM 分析时可能误将这些标记当成错误内容。建议增加 `MaskedOutput` 模式，使用语义化描述如 `***JWT_TOKEN_REDACTED***`。

### 8.2 场景二：表单智能填充与辅助（Copilot Form Filling）

| 维度 | 评估 |
|:---|:---|
| **状态** | 🟡 **中等成本，极高用户效率提升。建议在场景一之后执行。** |
| **核心技术** | AI 获取 Step 的 JSON Schema + 项目上下文 → 填充预览 → 用户 Diff 确认 → Dry Run 预校验 |

#### 代码基础设施评估

| 组件 | 文件 | 状态 | 说明 |
|:---|:---|:---:|:---|
| StepSpec 定义 | `pkg/pipeline/spec.go` | ✅ **可用** | 字段映射清晰，可生成 JSON Schema |
| 基础字段验证 | `pkg/pipeline/spec.go` Validate() | ✅ **可用** | 可复用为后端预校验 |
| DAG 拓扑验证 | `internal/pipeline/validate.go` ValidateDAG() | ✅ **可用** | 可复用为 Dry Run 的拓扑层校验 |
| 项目上下文获取 | — | 🔴 **缺失** | 需要从工作空间/Git 推断分支、语言、制品库等信息 |

#### 交互设计要点

1. **Diff 预览机制**（核心技术决策）：
   ```
   AI 填充后 → 不直接覆盖 → 以浅灰色/标记差异显示 → 用户点击 [采纳] 确认
   ```
   在采纳按钮旁建议增加 **「多方案轮换」** 箭头。AI 对同一字段可能有多个合理值（如镜像版本 `golang:1.22` vs `golang:1.23`），用户可在备选方案间切换。

2. **Dry Run 验证闭环**：
   ```
   AI 填入数据 → POST /api/v1/fill/dryrun → 
      ├─ Validate() 基础字段校验
      ├─ ValidateDAG() 拓扑校验（如有 depends_on 变更）
      └─ 返回校验结果 → 前端展示成功/失败标记
   ```

3. **字段级触发**：不一次性填充整个表单。在每个字段旁放 [✨ AI 填充] 小图标，用户按需点击。

#### 代码改动量

| 任务 | 估算 | 注意 |
|:---|:---:|:---|
| 后端 `POST /api/v1/fill/preview`（AI 填充预览） | 1-2 天 | 需要 LLM 接口已就绪 |
| 后端 `POST /api/v1/fill/dryrun`（复用现有 Validate 逻辑） | 0.5 天 | 主要是 API 封装 |
| 前端字段级 AI 填充图标 + Diff 展示 | 2-3 天 | 核心在 UI 交互设计 |
| 多方案切换支持 | 1 天 | 需后端返回候选项列表 |

#### 已知缺口

- `StepSpec.Cache.Key` 注释中提到支持 `{{ checksum "file" }}` 模板，但代码中没有解析逻辑。AI 填充时需要在 prompt 中明确告知不要填模板语法，或在填充后做模板预处理。
- 项目上下文获取（Git 分支、语言栈、制品库地址）目前没有实现，需要一个 `internal/context/` 包从工作空间扫描 `go.mod`/`package.json`/`pom.xml` 等文件推断。

### 8.3 场景三：AI 辅助编排（AI-Orchestrated Pipeline）

| 维度 | 评估 |
|:---|:---|
| **状态** | 🔴 **方向正确，但当前代码基础设施不足以支撑。建议前置条件积累完成后（场景一+场景二完成+Step 元数据标准化）再启动。** |
| **核心技术** | 自然语言 → Schema-Constrained LLM → PipelineSpec JSON → 可视化 DAG 预览 → 用户拖拽微调 → 最终提交 |

#### 需前置完成的依赖项

| 前置条件 | 对应 Issue/组件 | 当前状态 | 完成标志 |
|:---|:---|:---:|:---|
| **LLM 管线打通** | `internal/llm/` | 🔴 空壳 | LLMClient 接口可调用 |
| **Step 元数据标准化** | `StepSpec` 扩展 | 🔴 缺失 | 需添加 `InputSchema`、`OutputArti-facts`、`Tags`、`DocsURL` 字段 |
| **Step 注册表** | `internal/registry/` | 🔴 缺失 | 管理可用 Step 模板的注册中心 |
| **多轮对话状态管理** | `internal/llm/conversation.go` | 🔴 缺失 | 维护对话上下文和边界判定 |
| **Schema-Constrained 输出** | LLM 调用层 | 🔴 缺失 | JSON Schema 约束 LLM 输出格式 |
| **可视化 DAG 渲染 API** | `internal/api/` | 🔴 骨架 | 定义 `POST /api/v1/preview` 端点 |
| **DSL 配置版本化** | `pkg/pipeline/spec.go` | ⚠️ 部分 | 需要将 spec 拆分为独立的 JSON Schema 文件 |

#### Step 元数据扩展建议

当前的 `StepSpec` 不足以支撑 AI 编排。建议扩展为：

```go
type StepSpec struct {
    Name      string   `json:"name"`
    Image     string   `json:"image"`
    Commands  []string `json:"commands"`
    DependsOn []string `json:"depends_on,omitempty"`
    Cache     *Cache   `json:"cache,omitempty"`
    Env       []string `json:"env,omitempty"`

    // === AI 编排所需扩展字段 ===
    InputSchema     *JSONSchema `json:"input_schema,omitempty"`     // 输入参数的结构化定义
    OutputArtifacts []string    `json:"output_artifacts,omitempty"`  // 输出产物（如二进制、镜像）
    Tags            []string    `json:"tags,omitempty"`             // 标签：["build", "test", "deploy", "notification"]
    DocsURL         string      `json:"docs_url,omitempty"`         // 文档链接
    Description     string      `json:"description,omitempty"`      // 自然语言描述（AI 消费）
}
```

#### 推荐实现路径

```
用户输入 → NL 意图分析(LLM) → 
   ├─ 意图清晰 → 生成 PipelineSpec JSON（schema-constrained output）
   ├─ 意图模糊 → 反问澄清（multi-turn）→ 回到上一步
   ↓
前端渲染 DAG 预览 → 用户拖拽微调 → 最终确认 → 执行
```

#### 关键交互设计决策

建议的「编排预览 + 人类校验」流程：

1. **AI 生成 DAG 预览**：不直接保存，而是以可交互的流程图展示在前端
2. **用户拖拽微调**：用户可调整 Step 顺序、修改参数、增删节点
3. **确认提交**：用户确认后才写入配置库

这是 "AI 生成 → 人类校验 → 最终确认" 的协同模式，是目前云原生工具中用户体验最好的路径。与当前代码库的 `examples/go-ci.json` 结构天然对齐（checkout → test → build 可作为渲染示例）。

#### 交互恢复与状态一致性（重要）

参考白皮书 9.3.1 节的分析，AI 编排场景需要特别注意：

- 如果用户在 Copilot 模式下手动编辑了 DAG（删除某个步骤），已执行步骤的中间产物如何处理？
- **初期策略**：仅支持"从失败步骤开始全量重跑"，不做增量重试

#### 建议优先实施的子场景（场景 0.5 — 配置模板自动补全）

基于代码库分析，存在一个低成本高回报的过渡场景：

**需求**：`PipelineSpec` 验证通过后才能执行。但用户忘了填 `commands` 或 `image` 时，报错信息是硬编码的 `ErrStepNoCommands`/`ErrStepImageEmpty`。

**方案**：在用户保存前，AI 根据 `step.Name` 推断默认值（如 step name 为 "test" → 自动补 `commands: ["go test ./..."]`）。这是场景二的子集，但**不需要任何前端改造**，纯后端 lint 即可实现。

### 8.6 决策记录

| # | 问题 | 决策 | 备注 |
|:---|:---|:---|:---|
| 1 | 三个场景的执行顺序 | **场景一 → 场景二 → 场景三** | 先建信任（诊断），再提高效率（填充），最后做质变（编排） |
| 2 | RAG 种子库存放方式 | **静态 YAML（编译时嵌入） + SQLite 动态积累** | `seeds/` 做 few-shot，历史记录做动态上下文 |
| 3 | AI 填充的交互默认 | **Diff 预览 + 用户确认，不可直接覆盖** | 场景二的交互底线，防止 AI 幻觉导致配置错误 |
| 4 | 编排模式的默认路径 | **AI 生成 → 人类校验(DAG 预览) → 最终确认** | 参考白皮书 9.3.1 状态一致性分析 |
| 5 | 失败后重试策略 | **初期仅支持从失败步骤全量重跑** | 不做基于已有产物的增量重试，避免状态一致性问题 |
| 6 | 场景三启动条件 | **Milestone A + B 完成 + Step 元数据标准化 + 注册表就绪** | 不可跳过前置依赖 |
