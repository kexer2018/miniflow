# miniflow — AI 原生轻量级 CI/CD 执行引擎 实施方案

> **本文档定位**：技术方案 + 分阶段实施计划。讨论确认后据此动手编码。
>
> **核心原则**：Phase 1 独立发布，不等 Phase 2。CLI 先行，Web UI 后续。

---

## 一、技术栈锁定

| 层面 | 选型 | 理由 |
|:---|:---|:---|
| **后端语言** | **Go 1.23+** | 容器编排 + 网络分发，goroutine 天然胜任，Docker SDK 成熟，编译快速，招聘友好 |
| **容器 SDK** | `github.com/docker/docker/client` | 官方维护，API 覆盖全面 |
| **CLI 框架** | `github.com/spf13/cobra` | Go 生态 CLI 事实标准 |
| **日志/结构化** | `slog`（标准库）+ `encoding/json` | Go 1.21+ 自带，零依赖 |
| **数据库** | PostgreSQL（底座）+ Redis（缓存） | 白皮书 9.3.6 建议，Phase 1 先用 SQLite 简化 |
| **LLM SDK** | 标准 HTTP + SSE（模型无关抽象层） | 不绑定特定厂商 |

**不做 Rust 双轨并行**（白皮书 9.5 建议）。

## 三、Phase 1 详细方案：报错分析与自动修复提示

### 3.1 核心流程

```
用户执行流水线 (CLI)
    │
    ▼
Worker 逐 Step 拉起临时容器执行
    │
    ▼
某 Step 失败 → 容器 exit 1
    │
    ▼
collector 实时采集 Stdout/Stderr
    │
    ▼
sanitizer 脱敏（正则层）
    │
    ▼
classifier 分流
    ├── 应用代码错误 → 只读输出解析结果
    └── 基础设施错误 → analyzer 分析
                            │
                            ▼
                       LLM + RAG 种子库 → 生成修复建议卡片
                            │
                            ▼
                       输出建议到终端 + 询问是否重试
```

### 3.2 数据模型

```go
// Step 执行结果
type StepResult struct {
    Name       string `json:"name"`
    Status     string `json:"status"` // success / failed
    ExitCode   int    `json:"exit_code"`
    RawLog     string `json:"raw_log"`
    Sanitized  string `json:"sanitized_log"`
    DurationMs int64  `json:"duration_ms"`
}

// 日志分类结果
type Classification struct {
    Type    LogType // app_error | infra_error | unknown
    Reason  string
    Signals []string // 匹配到的信号词
}

type LogType string
const (
    AppError  LogType = "app_error"   // 只读解释
    InfraError LogType = "infra_error" // 触发修复流
    Unknown   LogType = "unknown"
)

// 修复建议
type FixSuggestion struct {
    StepName     string `json:"step_name"`
    RootCause    string `json:"root_cause"`
    FixPlan      string `json:"fix_plan"`
    Confident    float64 `json:"confident"` // 0-1
    SuggestedFix *StepFix `json:"suggested_fix,omitempty"`
}

type StepFix struct {
    Description string `json:"description"`
    // 覆盖的配置字段
    ConfigOverride map[string]any `json:"config_override"`
}
```

### 3.3 Log Classifier 分流规则（确定性的，不需要 LLM）

| 信号词 | 分类 | 示例 |
|:---|:---|:---|
| `panic:`, `SyntaxError`, `NullPointer`, `TypeError`, `undefined is not a function` | `app_error` | 应用代码抛异常 |
| `Traceback (most recent call last)` | `app_error` | Python 异常 |
| `exit code 1` + 无其他信号 | `unknown` | 兜底 |
| `401 Unauthorized`, `403 Forbidden` | `infra_error` | 鉴权失败 |
| `no such image`, `manifest not found` | `infra_error` | 镜像拉取失败 |
| `Connection refused`, `dial tcp`, `TLS handshake timeout` | `infra_error` | 网络连接问题 |
| `Permission denied`, `cannot open file` | `infra_error` | 文件权限问题 |
| `no space left on device` | `infra_error` | 磁盘空间不足 |
| `authentication required`, `certificate has expired` | `infra_error` | 凭证过期 |
| `could not find`, `not found` + 涉及 config/credential 上下文 | `infra_error` | 配置缺失 |

### 3.4 RAG 种子案例结构（Phase 1 手动构建 50-100 条）

```yaml
# seeds/image-pull.yaml
- id: "img-001"
  category: "image_pull"
  title: "镜像不存在于仓库"
  match_pattern:
    - "no such image"
    - "manifest for .* not found"
    - "not found: manifest unknown"
  raw_log_example: |
    docker: Error response from daemon: manifest for golang:1.99 not found: manifest unknown: manifest unknown.
  sanitized_log: |
    docker: Error response from daemon: manifest for <IMAGE> not found.
  root_cause: "指定的容器镜像标签在目标仓库中不存在（可能是拼写错误、标签名变更或仅存在于私有仓库）"
  fix_suggestion:
    description: "修正镜像标签为已存在的版本"
    config_override_example:
      image: "golang:1.22"
```

```go
// 所有容器统一以 UID 1000:1000 运行
// 启动前对共享工作空间执行 chown
func (m *Manager) EnsureWorkspacePermissions(workspacePath string) error {
    // docker run --rm -v workspacePath:/workspace --user 1000:1000 \
    //   alpine chown -R 1000:1000 /workspace
    // 约束：基础镜像必须支持 --user 1000 运行
}
```

### 5.2 日志脱敏第一层（正则覆盖 Top 80%）

```go
// 脱敏规则优先级由高到低
var sanitizeRules = []SanitizeRule{
    {Pattern: `Bearer\s+eyJ[a-zA-Z0-9_-]+\.eyJ[a-zA-Z0-9_-]+\.[a-zA-Z0-9_-]+`, Replace: "Bearer ***JWT***"},
    {Pattern: `AKIA[0-9A-Z]{16}`, Replace: "***AWS_KEY***"},   // AWS Access Key
    {Pattern: `(?:https?://)[^:]+:[^@]+@`, Replace: "***CREDENTIALS@"}, // Basic Auth in URL
    {Pattern: `-----BEGIN (?:RSA |EC |OPENSSH )?PRIVATE KEY-----`, Replace: "***PRIVATE_KEY***"},
    {Pattern: `[a-zA-Z0-9_\-]{40,}`, Replace: "***HIGH_ENTROPY***"}, // 高熵字符串兜底
}
```

### 5.3 Pipeline JSON Schema（Phase 1 支持的格式）

```json
{
  "version": "1.0",
  "name": "go-ci",
  "workspace": "/workspace/go-project",
  "steps": [
    {
      "name": "checkout",
      "image": "alpine/git:latest",
      "commands": ["git clone https://github.com/user/repo.git ."],
      "cache": false
    },
    {
      "name": "test",
      "image": "golang:1.22",
      "commands": ["go test ./..."],
      "depends_on": ["checkout"],
      "cache": {
        "path": "/go/pkg/mod",
        "key": "go-mod-{{ checksum \"go.sum\" }}"
      }
    }
  ]
}
```

### 5.4 错误处理原则

- **底层错误全部包装**：使用 `fmt.Errorf("context: %w", err)` 携带上下文
- **容器执行失败**：不 panic，返回清晰的 `StepResult`（含 ExitCode + 原始日志）
- **LLM 调用失败**：降级输出基础分析（"无法连接 AI 服务，以下为原始日志…"），不阻塞流程
- **脱敏失败**：保守策略——宁可漏脱敏不可误脱敏（白皮书 9.3.3 建议）

## 六、决策记录

> 以下为讨论确认后的决策，持续更新。

### ✅ 已确认

| # | 问题 | 决策 | 备注 |
|:---|:---|:---|:---|
| 1 | DAG 输入格式 | **JSON** | LLM 直接输出 JSON，前后端天然对齐，Go 标准库原生支持。后期可按需加 YAML 转换层 |
| 2 | LLM 厂商选择 | **抽象接口 `LLMClient`，默认 OpenAI 兼容协议** | 通过 `LLM_API_KEY` + `LLM_BASE_URL` 环境变量配置，DeepSeek/Qwen 等国产模型兼容此协议，后期可加 Claude 实现 |
| 3 | Phase 1 并行 Step | **仅串行** | 一个 Step 执行完再执行下一个，降低复杂度、日志归属清晰。并行放到 Phase 2 |
| 4 | 持久化方案 | **SQLite**（`modernc.org/sqlite`） | 纯 Go 实现，无需 CGO，轻量高性能。后期平滑迁移 PostgreSQL |
| 5 | 测试策略 | **分层策略：业务逻辑纯单元测试 + 容器层 dockertest 集成测试** | Log Classifier、修复引擎等无容器依赖的用标准 mock/单元测试；Docker SDK 封装用 dockertest 启动真实容器验证，少量核心场景即可 |
